# Simulated caller for a voice agent

A voice agent's timeline is the only one with the **whole chain** in it — the
caller's speech recognised, the turn ended, the model answering, the voice
synthesised — and every link of it stays empty until somebody talks to the agent.
This is that somebody: one synthetic caller that joins as an ordinary participant,
speaks through the project's TTS, and waits for the agent to finish replying
before saying the next line.

It publishes **no metrics and no transcriptions of its own**, so everything on the
room's metric topic came from the agent and the timeline reads exactly as it would
for a human caller. A simulator that reported its own STT would put two agents'
numbers in one plot, which is worse than having no plot.

The two-humans case — a support agent and a customer, nobody's speech generated by
a model — is `example/agent-assist-sim` instead.

## Run it

Settings → Access tokens → New token, then:

```bash
TOKEN=lkui_…

curl -s -X POST http://localhost:3010/api/voice-sim \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"sandbox": "test"}' | jq .run.summary
```

It answers when the call is over:

```json
{
  "room": "sim-test",
  "agentJoined": true,
  "spoken": ["Hi, can you hear me?", "…"],
  "replies": ["replied", "replied", "replied"],
  "transcript": [
    { "from": "agent-AJ_…", "text": "Hello! I am your friendly voice assistant." },
    { "from": "sim-user-62584", "text": "Hi, can you hear me?" }
  ],
  "metrics": {
    "stt_metrics": 3, "eou_metrics": 3, "eot_inference_metrics": 3,
    "llm_metrics": 4, "tts_metrics": 8
  }
}
```

`metrics` is the point: all five kinds present means the timeline will draw the
full chain. A missing kind localises the problem immediately — no `stt` and the
agent never heard the caller, no `eot` and the agent predates turn-detector
metrics (redeploy it from the Builder), no `llm`/`tts` and the models are not
answering.

`replies` says whether each turn was actually answered, read from the agent's own
`lk.agent.state` attribute. `"timeout"` means the agent never spoke before the
wait ran out — usually a cold model, sometimes no agent at all (`agentJoined`).

### Options

| field | default | |
|---|---|---|
| `sandbox` | — | supplies the agent to dispatch and the voice to speak with |
| `room` | `sim-<sandbox>` | its own room: history keeps one row per room name, so it cannot overwrite a real call's record |
| `agent` | the sandbox's *Dispatch to agent* | needed when the sandbox is on auto-dispatch, since a voice still has to come from an agent |
| `turns` | four lines about a broken connection | `["line", …]` — what the caller says |
| `gapMs` | 800 | silence after each line before waiting for the reply |
| `replyTimeoutMs` | 25000 | how long a reply may take before the turn is called unanswered |
| `drainMs` | 4000 | TTS metrics arrive after the audio has finished playing |
| `wait` | `true` | `false` returns a run id to poll with `GET /api/voice-sim?id=…` |

## Without the dashboard

Every run keeps its config under `data/sim-runs/`:

```bash
example/agent-starter-python/venv/bin/python \
  example/agent-voice-sim/simulate.py data/sim-runs/sim-xxxx.json
```

## Two things it must keep doing

- **Take turns from the agent's own state**, not from a fixed sleep. Talk over the
  agent and the run measures interruptions instead of a clean chain; wait too long
  and every turn costs seconds it did not need.
- **Push real silence between lines.** An absent track gives the agent's VAD no
  frames to hear a pause in, so the caller's turn never ends and no reply comes.
