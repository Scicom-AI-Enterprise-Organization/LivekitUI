# src/app/api — REST routes

Every route follows the same skeleton:

```ts
const session = await getSession();
if (!session) return NextResponse.json({ error: "Unauthorized" }, { status: 401 });
if (session.role === "member") return NextResponse.json({ error: "Insufficient permissions" }, { status: 403 });
```

Members are view-only: gate writes, leave reads open to any signed-in user. `getSession()` is required even though middleware ran — middleware cannot reach the database, so it only proves a cookie was present.

## Two families of route

**LiveKit-backed** (`rooms`, `sip-trunks`, `dispatch-rules`, `calls`, `egresses`, `ingresses`, `livekit/token`) — call the server SDK and wrap failures in `livekitError(error, "SIP", "list SIP trunks")`. Do not invent your own 503 text; the shared mapper is what lets pages distinguish "service not deployed" from "broken".

**Database-backed** (`providers`, `secrets`, `phone-numbers`, `agents`, `sandbox-apps`, `auth`, `webhooks`, `api-keys`, `tools`, `sessions`, `storage`) — go through `ensureDb()`. Validate and normalize input here, not in the page: trim, strip trailing slashes from URLs, drop blank rows, and reject values that end up in generated code or SQL against an allow-list (see `TTS_AUDIO_FORMATS`, `PROVIDER_PLUGINS`).

## Conventions

- Responses are shaped for the UI, camelCase, via `src/lib/api-serialize.ts` for protobuf types. List endpoints return `{ <plural>: [...], total }`.
- Never return a secret value unless explicitly asked *and* the caller is owner/admin (`/api/secrets?reveal=1`). Default responses carry a masked `preview`.
- Mutating an entity that another one references? Report it rather than cascading silently — `DELETE /api/secrets` returns `usedBy` listing providers still pointing at it.
- Routes that spawn processes or reach operator-supplied URLs (`agents/[id]/deploy`, `providers/test`) are admin-only and must time-box outbound requests (`AbortSignal.timeout`).

## Gotchas

- `/api/livekit/token` does not spawn anything. It creates a room, dispatches the **deployed** agent by name, and returns a participant token. Agents generated by the builder register with `agent_name=…`, i.e. explicit dispatch — nothing joins a room unless something dispatches it by name.
- Adding `/api/<new>` also means adding it to `DASHBOARD_PREFIXES` in `src/middleware.ts`, or a request whose referer is a sandbox will be proxied into the sandbox instead.
- `POST /api/sessions` is deliberately open to members: they can run a console session, so their sessions have to be able to save themselves. Deleting one still requires a writer.
- `/api/webhooks/livekit` is the only trigger for server-side session capture: `room_started` spawns an observer, `room_finished` adopts what it wrote. Capture failures are caught and logged rather than returned — LiveKit retries a non-200, and a retry storm is worse than a missing recording. `GET /api/sessions` adopts too, which is what covers a capture written while the dashboard was restarting.
- `/api/sessions/capture` is the switch for that (off by default), not a session endpoint. It sits under `/api/sessions/` so the static segment wins over `[id]`; its GET also lists the observers running right now.
- `/api/agents/[id]/recordings/*` reads through `src/lib/storage.ts`, so it can fail because a *bucket* is unreachable, not just because a file is missing — that is the 502 rather than the 404.
- `/api/auth/*` is in `PUBLIC_PATHS`; those routes must do their own session checks.
